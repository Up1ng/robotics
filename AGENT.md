# Контекст проекта и правила для следующих лабораторных

Этот файл нужен агенту, который продолжает работу после нового сеанса или потери контекста. Перед выполнением следующей лабораторной прочитай его, актуальное задание и состояние Git. После завершения работы обнови раздел с выполненными лабораторными. Новые прямые указания пользователя имеют приоритет над этим файлом.

## Проект и цель

- Курс: «Робототехника» НГУ, материалы курса — `https://ros.lms.ci.nsu.ru/`.
- Локальный репозиторий: `/home/uping/project/nsu/robotics`.
- GitHub: `https://github.com/Up1ng/robotics`, remote `origin` использует SSH.
- Пользователь передаёт задания в папках со скриншотами или архивах. ПР01 была в `скрины_сайта_курса/`, ПР02 — в `lab2/`; в рабочем каталоге также есть `lab2.zip`.
- Требуется выполнить лабораторную целиком: прочитать условия, реализовать нужные файлы, провести реальные опыты, оформить evidence, проверить сдачу. Если пользователь поручил push, запушить отдельную ветку и дать ссылку.
- Пользователь предпочитает русский язык и простые объяснения с примерами из его лабораторных. Он несколько раз просил доделать работу; не заканчивай ответ одним планом, если можешь продолжать выполнение.

## Источники требований

1. Прямые актуальные указания пользователя.
2. Скриншоты и файлы задания соответствующей лабораторной: прочитай все страницы, включая порядок сдачи и критерии проверки. Изображения нужно действительно просмотреть; нельзя восстановить задание только по названиям файлов.
3. Манифест, шаблоны и checker соответствующей версии course-kit.
4. Существующие README, исходники и evidence — образцы реализации и прошлых опытов; они не заменяют условия новой лабораторной.

Не распространяй требования ПР01/ПР02 на новые задания без проверки. Если материалов не хватает, сначала исследуй доступные файлы и архивы, затем задай конкретный вопрос о недостающем условии. При наличии доступа к сети уточняй технические детали по официальной документации именно используемого дистрибутива ROS.

## Среда: работать через Docker

Пользователь явно потребовал выполнять лабораторные через Docker, поскольку это рекомендовано в скриншотах курса.

- ROS, Gazebo, `colcon`, зависимости и учебные процессы запускай внутри контейнера. Репозиторий и материалы остаются на хосте и монтируются в контейнер.
- Не устанавливай ROS на хост ради выполнения лабораторной. Хостовые средства вроде Docker и доступа к графическому дисплею настраивай по необходимости.
- Не подключай NetBird и не создавай VPN: для прошлых лабораторных это не требовалось. Если новое задание прямо требует сетевую инфраструктуру, руководствуйся его условиями.
- Пользователь разрешал установку и скачивание необходимых зависимостей. Продолжай обычные необходимые действия без повторного запроса разрешения; учитывай действующие ограничения среды выполнения.
- Не сохраняй пароль sudo, токены, ключи и другие секреты в репозитории, отчётах или этом файле. Если доступ перестал работать, сообщи конкретную ошибку, не считай старые данные гарантированно актуальными.

## Ветки, изменения и сдача

- Каждая лабораторная выполняется в отдельной ветке. Использованное соглашение: `pr01`, `pr02`; следующие — `pr03`, `pr04` и так далее.
- Перед работой проверь `git status`, текущую ветку, существующие локальные/удалённые ветки и историю. При просьбе «доделай» продолжай имеющуюся ветку нужной лабораторной.
- Основание новой ветки выбирай по заданию и зависимостям: используй `main` для самостоятельной работы или нужную предыдущую ветку, если новое задание продолжает её. Не предполагай, что `main` уже содержит прошлые лабораторные.
- Не удаляй и не перезаписывай чужие или пользовательские незакоммиченные изменения. При необходимости используй отдельный worktree. Учитывай перенос `AGENT.md` и `AGENTS.md` в новую ветку: это общий контекст, и его нельзя потерять при переключении.
- Добавляй в коммит только относящиеся к работе файлы. Не коммить `build/`, `install/`, `log/`, кэши и материалы задания автоматически. Существующий закреплённый архив checker в `.github/ci/` — намеренное исключение.
- Для первых двух работ сначала делался коммит реализации, затем отдельный коммит evidence. Поле `report.json.commit` содержит полный SHA коммита реализации, а ссылка сдачи может указывать на последующий коммит с evidence. Проверь этот порядок в условиях следующей работы.
- При поручении выполнить лабораторную и запушить результат заверши обычный push своей ветки без дополнительного согласования. Не используй force push, не сливай в `main` и не создавай PR без соответствующего поручения или требования задания.
- После push проверь удалённую ветку и, если CI требуется для сдачи, результат workflow. Если проверка ещё идёт или упала, укажи это честно и продолжи устранять относящуюся к работе проблему.
- В итоговом ответе дай ссылку вида `https://github.com/Up1ng/robotics/tree/prNN`; если требуются, добавь полный SHA сдачи и ссылку на успешный CI run.
- Просьба создать документацию сама по себе не означает поручение коммитить или пушить её.

## Пояснения ROS, которые пользователь уже спрашивал

- **RMW** — адаптер между ROS 2 и библиотекой обмена сообщениями. `rmw_fastrtps_cpp` использует eProsima Fast DDS, `rmw_cyclonedds_cpp` — Eclipse Cyclone DDS. Меняются реализация обнаружения, транспорт, настройки и характеристики обмена; нельзя обещать, что одна всегда быстрее. `cpp` означает реализацию адаптера на C++, а не запрет Python-нод.
- **`RMW_IMPLEMENTATION`** выбирает установленный адаптер при запуске процессов. Поле `rmw_implementation` в прошлой `environment.json` записывало результат опыта, а не переключало ROS. Перед сменой реализации останови соответствующие процессы и учти ROS CLI daemon.
- **`ROS_DOMAIN_ID`** разделяет группы узлов: одинаковый номер нужен для обнаружения и обмена в одной группе. Это полезно в общей сети аудитории; в одиночной изолированной среде обычно достаточно значения по умолчанию `0`. Домен не является механизмом защиты доступа. Изменение переменной в оболочке не меняет уже запущенные процессы.
- **QoS profile** задаётся для конкретного издателя/подписчика. `reliability` — повторять потерянное (`reliable`) или допускать потери (`best_effort`); `durability` — только новые сообщения (`volatile`) или хранить данные для поздних подписчиков (`transient_local`); `history/depth` — очередь. `deadline` — ожидаемый интервал сообщений; `lifespan` — срок годности; `liveliness/lease_duration` — подтверждение работоспособности и время ожидания.
- **Совместимость QoS**: подписчик не должен требовать больше предложенного издателем. `best_effort` издатель с `reliable` подписчиком несовместим; обратная комбинация совместима. `volatile` издатель с `transient_local` подписчиком несовместим; обратная комбинация даёт новые сообщения. Для старых сохранённых сообщений обе стороны используют `transient_local`. Предложенные `deadline` и `lease_duration` должны быть не больше запрошенных. `automatic` издатель не удовлетворяет требованию `manual_by_topic`. Различия очередей сами по себе не запрещают соединение. Совпадение имени, типа и домена также необходимо, но не гарантирует связь при сетевых проблемах.
- **Launch-файл** хранит воспроизводимый запуск узлов и их параметры, имена, namespaces и remappings. Bringup-пакет собирает launch и конфигурации системы; собственные алгоритмы или ноды для него необязательны.

При объяснении сначала приведи один конкретный пример, затем назови термин. Не перегружай ответ всеми настройками одновременно. Если пользователь просит объяснить проще, перестрой объяснение, а не повторяй прежний текст.
